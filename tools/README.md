# CM Encoder / Renderer — draft v0.1 (engineering prototype)

Реализация Phase 0/1 из `CM_Encoder_Scanner_Decoder_v0.1.txt` (§42): первый
детерминированный Circle Mark, который генерируется из конкретного Entity ID
алгоритмом, а не рисуется вручную. Только стандартная библиотека Python 3
(без pip-зависимостей).

**Статус: инженерный прототип.** Ничего здесь не является CM Encoding
Profile 1.0. Спецификация прямо запрещает фиксировать до camera/print
benchmark: число колец, число секторов, "2 бита/сектор" как финальную схему,
% ECC, минимальный размер метки, максимальную дистанцию/угол считывания,
% допустимого повреждения (§43 encoder-спецификации, §23 визуальной
спецификации). Всё это ниже — конкретный **рабочий выбор для первого
прототипа**, помеченный как проектный (design placeholder), а не стандарт.

## Файлы

| Файл | Назначение |
|---|---|
| `cm_encoder.py` | Библиотека + CLI: `encode_payload`, `to_sectors`, `decode_sectors`, `decode_payload` |
| `cm_render.py` | Библиотека + CLI: `render_svg` — векторный (SVG) рендерер |
| `test_cm_roundtrip.py` | Самопроверка: CRC, round-trip, детект повреждений, валидность SVG |

## Быстрый старт

```bash
# только encode + round-trip decode в консоль
python3 cm_encoder.py --entity-id 0199a3f7-8c21-7d4e-b6a9-2f5e8c1d4a70 \
  --namespace bizdnai --type-hint document

# encode + render в SVG
python3 cm_render.py --entity-id 0199a3f7-8c21-7d4e-b6a9-2f5e8c1d4a70 \
  --namespace bizdnai --type-hint document --accent-core \
  --out ../examples/genesis/cyrqode-genesis-mark.svg

# самопроверка
python3 test_cm_roundtrip.py -v
```

## Логический payload (§6) — что кодируется и что НЕ кодируется

**Кодируется только:**

| Поле | Бит | Значение для genesis mark |
|---|---|---|
| Magic/Family | 8 | `0xC3` (фиксированная сигнатура семейства CM) |
| CM Version | 4 | `0` |
| Encoding Profile | 4 | `1` (`cm-v0.1-draft-a`) |
| Namespace Hint | 8 | `bizdnai` → код `1` |
| Entity ID | 128 | `0199a3f7-8c21-7d4e-b6a9-2f5e8c1d4a70` |
| Resolver Hint | 8 | `default` → код `0` |
| Type Hint | 4 | `document` → код `3` |
| Reserved | 76 | все нули (v0.1) |
| Integrity (CRC-16/CCITT-FALSE) | 16 | вычисляется над всеми полями выше |
| **Итого** | **256** | = ёмкость профиля, ровно 100% заполнение |

**Прямо НЕ кодируется** (§6 "MUST NOT", §16 визуальной спецификации): имя,
дата, автор, владелец, цена, ATI/рейтинг, местоположение, статус,
срок годности, роль сотрудника, текст/URL внутри кодовой области. В
`cyrqode-genesis-mark.svg` из переменных данных присутствует только
Entity ID (то, для чего и существует Circle Mark) — никаких персональных
или изменяемых атрибутов.

Хватает ли 128 бит на Entity ID со служебными полями: да, с большим
запасом — на служебные поля ушло 52 бита (Magic+Version+Profile+
Namespace+Resolver+Type), на Integrity 16 бит, итого 128+52+16=196 бит из
256 доступных; оставшиеся 76 бит ушли в явный Reserved (не "случайный
запас", а обозначенная под будущее расширение ёмкость — см. §6 "Reserved —
MUST reserve capacity").

## Namespace / Type / Resolver hint — компактные коды, не строки

Спецификация описывает эти поля как *компактные* указатели ("Namespace
Hint — компактное указание", "Resolver Hint — маршрут... без жёсткой
привязки к одному домену"), а не как полные строки/URL внутри кодовой
области (что прямо запрещено §12 визуальной спецификации: "URL, длинные
тексты и цифры внутри кодовой области"). Поэтому в `cm_encoder.py` они
реализованы как маленькие реестры `int -> str`:

```python
NAMESPACE_TABLE = {"unspecified": 0, "bizdnai": 1}
TYPE_HINT_TABLE = {"unspecified": 0, "product": 1, ..., "document": 3, ...}
RESOLVER_HINT_TABLE = {"default": 0}
```

Это минимальные рабочие реестры v0.1, рассчитанные на расширение в будущих
версиях профиля (ширина полей — 8/8/4 бита — оставляет запас: 256/256/16
значений соответственно).

## Sector State — грамматика §8

2 бита на сектор, 4 состояния — **исследовательский baseline**, спецификация
прямо говорит, что после benchmark он MAY быть заменён (§8 encoder-спека):

| Код | Состояние | Геометрия |
|---|---|---|
| `00` | EMPTY | нет штриха |
| `01` | INNER | штрих во внутренней половине радиального диапазона кольца |
| `10` | OUTER | штрих во внешней половине |
| `11` | FULL | штрих на весь допустимый радиальный диапазон |

Значение сектора — это просто `int(bits, 2)` двухбитного фрагмента, поэтому
маппинг кода на состояние получается автоматически из порядка констант
`STATE_EMPTY=0, STATE_INNER=1, STATE_OUTER=2, STATE_FULL=3` — таблица выше
выполняется "по построению", без отдельной ветки соответствия.

## Encoding Profile "cm-v0.1-draft-a" (profile_id=1) — геометрия

**Проектный выбор, не финал:**

- 4 кольца данных × 32 сектора × 2 бита = **256 бит ёмкости**;
- 1 дополнительное физическое Parity/ECC-кольцо (32 сектора, та же
  4-состояний грамматика) — не входит в ёмкость логического payload, это
  отдельный физический уровень избыточности (см. "Interleaving и
  межкольцевое кодирование" ниже);
- 1 Sync/Orientation-кольцо с 4 маркерами (не несёт бит payload, §11);
- CM Core в центре — фиксированный "bullseye" (заливка + белое кольцо-вырез
  + точка), одинаковый для всех меток, не несёт Entity ID (§10).

32 сектора на кольцо и 4 кольца данных выбраны так, чтобы:
1. заполнить 256-битную ёмкость ровно, без "лишнего" необъяснённого
   остатка (структура: 128 символов × 2 бита);
2. дать interleaver'у (см. ниже) квадратно-подобную матрицу 8×16 для
   разумного разноса соседних бит.

Это **не** результат camera-benchmark — финальные числа определяются после
"Phase 4 — Print Benchmark" (§42 encoder-спецификации).

## Interleaving (§9) — как устроено

Раздел 9 требует: "Interleaving SHOULD разносить соседние логические биты
по физически удалённым позициям", чтобы локальное повреждение не убивало
один непрерывный блок payload.

Реализован простой **детерминированный блочный interleaver** на уровне
2-битных символов (не отдельных бит — символ = одна физическая сектор-
ячейка):

1. 128 логических символов payload (`s = 0..127`) записываются **построчно**
   в матрицу `8 строк × 16 столбцов` (`row = s // 16, col = s % 16`).
2. Физический порядок ячеек — **чтение по столбцам**: физическая позиция
   `p = col * 8 + row`.
3. Физическая позиция `p` (`0..127`) отображается на `(ring, sector)` как
   `ring = p // 32, sector = p % 32` — то есть кольцо 0 занимает первые 32
   физические позиции, кольцо 1 — следующие 32, и т.д.

Эффект: два логически соседних символа (`s` и `s+1`, одна строка исходной
матрицы) оказываются на расстоянии ровно **8 физических ячеек** друг от
друга (`test_interleaving_disperses_neighbours` в
`test_cm_roundtrip.py` проверяет это программно) — т.е. в среднем на
четверть оборота одного кольца, а иногда и в другом кольце. Это не
Reed-Solomon и не заявляется как доказанная защита от конкретного % площади
повреждения (§16 явно не фиксирует алгоритм ECC) — только простое,
детерминированное, проверяемое разнесение соседних бит.

## Межкольцевая Parity (дополнительный физический уровень, не логический payload)

Помимо interleaving внутри логического потока, реализован простой
**физический parity-хук** по требованию §9 ("вертикальный по r набор
состояний в одной θ-позиции может формировать parity/codeword"):

Для каждой угловой позиции `sector` (0..31) значение Parity-кольца =
XOR четырёх состояний (0..3) колец данных 0..3 в этой позиции:

```python
parity[sector] = data[0][sector] ^ data[1][sector] ^ data[2][sector] ^ data[3][sector]
```

`decode_sectors` пересчитывает эту XOR-сумму и сравнивает с реально
прочитанным Parity-кольцом; несовпадение попадает в `parity_mismatches`.
**Важно — это НЕ полноценный ECC**: одна parity-позиция на столбец не
позволяет ни однозначно локализовать, ни исправить ошибку при
одновременном повреждении нескольких колец в одном столбце — это просто
дополнительный, дешёвый детектор несогласованности, дополняющий CRC.
Настоящий ECC-алгоритм (Reed-Solomon/BCH и т.п., §16) сознательно не
выбран — раздел 16 спецификации прямо оставляет это открытым.

## Integrity — почему CRC-16/CCITT-FALSE

- `poly=0x1021, init=0xFFFF`, без reflect-in/out и без final xor;
- выбран, а не CRC-32, потому что вдвое дешевле по битовому бюджету
  (256-битная ёмкость и так тесная под 128-битный Entity ID), а сам
  раздел 16 явно не требует конкретного алгоритма и оставляет его
  версионируемым/заменяемым;
- легко независимо проверяется: `crc16_ccitt_false_bytes(b"123456789") ==
  0x29B1` — общеизвестный тестовый вектор, используется в тестах;
- в проекте есть **две реализации** — побайтовая (для сверки с тестовым
  вектором) и побитовая (`crc16_ccitt_false_bits`, применяется к
  реальному payload, т.к. поля до CRC суммарно дают 180 бит — не кратно
  8). Тесты проверяют их эквивалентность на случайных данных.

CRC — это MUST-минимум "Integrity" из §6, а не финальный
crypto/ECC-suite; §16 прямо говорит, что архитектура должна позволять
версионировать ECC независимо от Entity ID — CRC-16 живёт в одном явном
поле Integrity и в будущем может быть расширен/заменён без переопределения
формата остального payload.

## Renderer (`cm_render.py`) — геометрия SVG

`viewBox="0 0 1000 1000"`, единый центр `(500, 500)`. Радиусы посчитаны
цепочкой от центра наружу (см. константы в файле), от центра к краю:

1. **CM Core** (§10): `r=0..176`, фиксированный "bullseye" (заливка,
   белое кольцо-вырез `r=130`, точка `r=65`) — одинаков для всех меток,
   Entity ID не несёт.
2. Зазор 14 → **Sync/Orientation-кольцо** (§11): `r=190..234`, 4 маркера
   разной ширины (`50°/40°/30°/20°`) и разной формы (`SOLID / OUTER_HALF /
   INNER_HALF / SPLIT`) на базовых углах `0°/90°/180°/270°` — не 3
   квадрата QR/Data Matrix, ассиметрия по построению снимает
   4-кратную неоднозначность поворота.
3. Зазор 12 → 4 **кольца данных** (`r=246..384`, каждое толщиной 30,
   зазор между кольцами 6): кольцо 0 (внутреннее) → кольцо 3 (внешнее).
4. Зазор 6 → **Parity/ECC-кольцо** (`r=390..420`).
5. **Quiet zone**: `r=420..500` (край канвы) остаётся пустым.

При `PARITY_OUT_R=420` и канве `1000×1000` сама метка (без quiet zone)
занимает `2×420/1000 = 84%` кадра — попадает в требуемый диапазон 80–85%
(§20 визуальной спецификации, п.20 "ЦМ занимает ориентировочно 80-85%
кадра").

**Состояние → геометрия внутри кольца:** `EMPTY` — ничего; `INNER` — дуга
во внутренней половине толщины кольца; `OUTER` — во внешней половине;
`FULL` — на всю толщину. Между соседними секторами оставлен угловой зазор
16% от углового шага (`SECTOR_GAP_FRACTION`) — чистое геометрическое
разделение для сегментации decoder'ом (§21 визуальной спецификации).

**Цвет:** по умолчанию строго монохромно (`ink=#04101F` тёмный на белом
фоне) — все элементы, несущие информацию (Sync/Orientation, Data rings,
Parity), рисуются только в `ink`, без параметра цвета. Флаг
`--accent-core` красит **только** CM Core в фирменный `#4800FF`
(фиолетовый) — это разрешено спецификацией явно, т.к. Core не несёт
уникальный Entity ID и является "non-essential layer, не меняющий decode"
(§20, §10). Чёрно-белая копия/печать/факс остаётся полностью декодируемой,
т.к. ни один бит payload не закодирован цветом.

## Что НЕ обещано (намеренно)

Раздел 43 encoder-спецификации и раздел 23 визуальной спецификации прямо
запрещают фиксировать до benchmark — и этот прототип ничего из
перечисленного не заявляет:

- процент восстановления после повреждения (детект — да, гарантированное
  восстановление — нет: у нас простая parity-подсказка, не полноценный
  ECC);
- дальность/угол считывания камерой;
- время распознавания;
- минимальный физический размер печати;
- финальность 4 колец / 32 секторов / 2 бит-на-сектор — это рабочий
  прототип Phase 1, а не CM Encoding Profile 1.0 (Phase 5, §42).

## Что зафиксировано уже сейчас (и почему)
