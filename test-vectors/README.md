# Тестовые векторы канонизации BUIP

Этот каталог содержит **самодостаточные** тестовые векторы для проверки
любой реализации канонизации JSON по RFC 8785 (JCS), совместимой с Circle
Mark. Они не зависят от Python-кода в `sdk/python` — тот код лишь один из
способов их получить и один из способов их проверить.

## Файлы

- `canonicalization.json` — массив тестовых случаев `{name, description,
  input, canonical, sha256}`.
- `signing.json` — тестовые векторы подписи событий (профили
  `ed25519-sha256-v1` и `ecdsa-p256-sha256-v1`) с фиксированными тестовыми
  ключами; подробнее — раздел "Подпись событий" ниже.
- `verify.py` — скрипт, который прогоняет `canonicalization.json` через
  референсную Python-реализацию (`sdk/python/buip_canonical.py`),
  `signing.json` через `sdk/python/buip_signing.py`, и дополнительно
  (опционально) валидирует `examples/*.json` по схемам из `schemas/`.

## Формат одного тестового случая

```json
{
  "name": "key_sorting_flat",
  "description": "человекочитаемое описание, что именно проверяет случай",
  "input": { "b": 2, "a": 1, "c": 3 },
  "canonical": "{\"a\":1,\"b\":2,\"c\":3}",
  "sha256": "e6a3385fb77c287a712e7f406a451727f0625041823ecf23bea7ef39b2e39805"
}
```

- `input` — уже разобранное JSON-значение (объект/массив/строка/число/
  булево/`null`). Ваш код должен взять именно эту распарсенную структуру
  (или эквивалент на вашем языке — dict/map/struct) и канонизировать её.
- `canonical` — ожидаемая каноническая строка, **как текст** (для удобства
  чтения глазами и сравнения построчно). При сравнении сопоставляйте байты
  UTF-8 этой строки, а не JSON-escaped форму, в которой она лежит в файле.
- `sha256` — `SHA-256` от **байтов UTF-8** строки `canonical`, в виде
  hex-строки в нижнем регистре (64 символа).

## Как использовать при написании своего SDK

1. Реализуйте функцию `canonicalize(value) -> bytes`, следуя
   `spec/canonicalization.md`.
2. Для каждого случая из `canonicalization.json`:
   - распарсите JSON-документ целиком через ваш стандартный JSON-парсер;
   - возьмите поле `input` как разобранную структуру;
   - вызовите вашу `canonicalize(input)`;
   - сравните результат **побайтово** (UTF-8) со значением поля
     `canonical`;
   - посчитайте `SHA-256` от результата и сравните hex-строку с полем
     `sha256`.
3. Все случаи должны совпасть **точно**, без исключений типа "почти
   совпадает" — расхождение даже в один пробел или порядок ключей означает,
   что подпись, посчитанная по вашей канонизации, не будет проверяться
   реализациями других участников экосистемы CYRQODE.
4. Отдельно обратите внимание на случай `rfc8785_french_reference_vector` —
   это независимо проверяемый эталонный вектор из публичного тестового
   набора RFC 8785/JCS (т.н. "French" vector), а не придуманный для этого
   репозитория пример. Если ваша реализация сходится с ним, это сильный
   сигнал совместимости с эталонным JCS-поведением, а не только с этим
   репозиторием.

## Что специально покрыто набором

- сортировка ключей объекта (плоская и во вложенных объектах);
- сохранение порядка элементов массива;
- юникод/кириллица без `\u`-экранирования;
- числа: целые (в т.ч. отрицательные и ноль), дробные, `-0`, экспоненциальная
  запись и пороги переключения на неё;
- булевы значения и `null`;
- пустой объект и пустой массив;
- экранирование кавычек, обратного слэша, переводов строк и прочих
  управляющих символов; отсутствие экранирования `/`.

## Чего в наборе нет (сознательно)

- Векторов для CBOR/COSE-профиля — вне рамок v0.1.

## Подпись событий

Отдельный файл — `signing.json`. Он не про канонизацию как таковую (та уже
проверена выше), а про то, что происходит с каноническими байтами дальше:
их подписывают. Решение о том, чем именно подписывать, зафиксировано
владельцем протокола в `spec/adr/0001-crypto-and-identifiers.md`;
человекочитаемое руководство с примерами кода — `spec/signing.md`;
референсная реализация — `sdk/python/buip_signing.py`.

### Что именно подписывается и почему серверные поля исключены

Подписывается не всё событие, а `signing_input(event)` — каноническое
(RFC 8785/JCS) представление события **без** `received_time`,
`committed_time`, `stream_sequence` (их проставляет сервер при приёме — у
клиента их ещё нет в момент подписания) и **без** самого поля `signature`
(иначе подпись подписывала бы саму себя). Дальше берётся SHA-256 от этих
байт, и уже этот 32-байтовый дайджест подписывается алгоритмом, который
определяет `crypto_suite`.

Практическое следствие для тех, кто проверяет подпись по записи из
журнала: событие после приёма сервером содержит три лишних поля, которых
не было при подписании — их обязательно нужно убрать (как и `signature`)
до канонизации, иначе подпись «не сойдётся» даже будучи корректной. Именно
поэтому в `signing.json` для каждого профиля показаны сразу два вида
события — `event` (как у клиента в момент подписи) и
`event_after_server_commit` (то же самое плюс серверные поля) — оба
проверяются с одинаковым результатом `verify_expected: true`.

### Чем отличаются два профиля

| `crypto_suite` | Алгоритм | Где применяется |
|---|---|---|
| `ed25519-sha256-v1` | Ed25519 (RFC 8032) над SHA-256(signing_input) | серверы, SDK, мобильные приложения |
| `ecdsa-p256-sha256-v1` | ECDSA P-256 над SHA-256(signing_input), prehashed | смарт-карты, NFC secure element, HSM |

Внешний API (`sign`/`verify`/`generate_keypair`) одинаков для обоих —
отличается только строка `suite` и тип ключа.

### Почему вектор ECDSA проверяется иначе, чем вектор Ed25519

**Ed25519 детерминирован**: один и тот же вход с одним и тем же ключом
всегда даёт побайтово одинаковую подпись. Поэтому в `signing.json` для
профиля `ed25519-sha256-v1` поле `signature_b64url` — это эталон:
сравнивайте свою подпись с ним строкой, побайтово.

**ECDSA P-256 недетерминирован**: подпись использует случайный nonce, и
каждый вызов `sign()` над тем же входом с тем же ключом даёт другую
подпись. Поэтому для профиля `ecdsa-p256-sha256-v1` значение
`signature_b64url` в векторе — это **один конкретный пример**, а не
эталон для сравнения строкой; сравнение подписи побайтово со своей
реализацией гарантированно разойдётся даже у корректной реализации.
Правильная проверка: приведённая подпись проходит `verify()` с
приведённым публичным ключом (`verify_expected: true`), и подпись,
посчитанная вашей собственной реализацией над тем же `signing_input`,
тоже проходит `verify()` с тем же ключом. Каждый профиль в `signing.json`
несёт поле `deterministic` (`true`/`false`) именно для того, чтобы это
нельзя было перепутать программно.

### Отрицательный случай

Для обоих профилей в `signing.json` есть случай `*_tampered_field_must_fail`
— то же событие с изменённым клиентским полем (`payload.quantity`) и той
же подписью, скопированной из валидного случая. `verify_expected: false`
здесь обязателен: изменение любого подписанного поля должно ломать
проверку, иначе подпись ничего не защищает.

### Тестовые ключи

Приватные и публичные ключи в `signing.json` — тестовые, сгенерированы
один раз при создании этого файла и не используются нигде за пределами
этих векторов. Формат: приватный ключ — PEM/PKCS8 без шифрования,
публичный — PEM/SPKI и дополнительно компактная raw base64url-форма (32
байта для Ed25519, 65 байт — несжатая точка кривой — для ECDSA P-256).

## Проверка референсной реализации

```bash
python3 test-vectors/verify.py
```

Скрипт возвращает ненулевой код завершения, если хотя бы один случай
канонизации или подписи разошёлся с ожидаемым значением. Если в окружении
не установлен пакет `jsonschema`, валидация примеров по схемам
пропускается с явным предупреждением; если не установлен пакет
`cryptography`, аналогично явно пропускается (SKIP, не тихий успех)
проверка `signing.json`. Проверка самой канонизации при этом выполняется
всегда и является обязательной частью прогона.

## Первое, обо что спотыкаются

Соблазн реализовать канонизацию «в одну строку» средствами стандартной
библиотеки. В Python это выглядит так:

```python
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

**Так делать нельзя.** На большинстве случаев результат совпадёт, и это самое
опасное: расхождение вылезет позже, на реальных данных. Конкретный пример из
вектора `mixed_realistic_event_fragment`:

| Значение | `json.dumps` | Правильно по RFC 8785 |
|---|---|---|
| `1.0` | `1.0` | `1` |

Числа канонизируются по правилам ECMAScript `Number::toString`, где дробное
значение без дробной части печатается как целое. Одна такая величина в событии —
и хэш разойдётся, а подпись не сойдётся.

Аналогичные расхождения дают сортировка ключей (по UTF-16 code units, а не по
code point) и представление очень больших и очень малых чисел.

Поэтому и нужны векторы: прогоните их до того, как начнёте подписывать события.
