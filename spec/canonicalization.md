# Канонизация JSON в BUIP (RFC 8785 / JCS)

## Зачем это вообще нужно

Хэш и подпись считаются не над «событием» как абстракцией, а над конкретной
последовательностью байт. Один и тот же логический объект `{"a": 1, "b": 2}`
можно сериализовать в JSON десятками разных, но семантически эквивалентных
способов:

```json
{"a": 1, "b": 2}
{"b": 2, "a": 1}
{ "a": 1, "b": 2 }
{"a":1.0,"b":2}
{"a": 1, "b": 2, }
```

Все эти строки означают «один и тот же» JSON-объект. Но `SHA-256` этих строк
— разные. Если издатель события сериализует его одним способом, а получатель
для проверки подписи пересобирает JSON своим сериализатором (другой порядок
ключей, другое форматирование чисел, другой набор пробелов) — хэш не
совпадёт, и корректная, неповреждённая подпись окажется «невалидной»
исключительно из-за различий сериализации, а не из-за подмены данных.

Для BUIP это критично, потому что:

- события подписываются один раз издателем и проверяются многократно,
  произвольным числом независимых сторонних SDK (JS/Python/Go/Rust/Java —
  см. раздел 33.2 протокольного ТЗ, требование cross-language
  compatibility);
- журнал append-only и рассчитан на десятилетия хранения — сериализатор,
  которым событие подписали в 2026 году, не обязан быть тем же кодом,
  которым его проверяют в 2036-м;
- BUIP — открытый протокол: сторонние разработчики пишут SDK
  независимо друг от друга, и единственный способ гарантировать, что их
  реализации дают один и тот же хэш — зафиксировать канонизацию как строгий,
  детерминированный, тестируемый алгоритм, а не как «использует json.dumps».

Поэтому: **прежде чем что-либо хэшировать или подписывать, объект MUST быть
приведён к единственно возможному каноническому байтовому представлению.**
Базовый профиль BUIP v0.1 — [RFC 8785 JSON Canonicalization Scheme
(JCS)](https://www.rfc-editor.org/rfc/rfc8785.html), как и указано в разделе
7 протокольного ТЗ.

## Область действия

Канонизации подлежит JSON-**значение** (объект, массив, строка, число,
булево, `null`) в его *разобранном* (parsed) виде — то есть смысл входа
уже определён парсером JSON, и канонизация работает с абстрактной моделью
данных (dict/list/str/number/bool/None в терминах Python), а не с
исходной строкой байт. Два JSON-документа, различающихся только
форматированием, но дающих одинаковую разобранную модель данных, обязаны
давать один и тот же канонический результат.

Канонизации подвергается ровно тот JSON-объект, который входит в поле
`payload` события или в тело сущности/связи при хэшировании/подписании.
Поля, специфичные для транспорта (например, HTTP-заголовки), в канонизацию
не входят.

## Правила канонизации

### 1. Сортировка ключей объекта

Ключи каждого JSON-объекта сортируются лексикографически по значению их
**UTF-16 code units** — именно так определяет сортировку RFC 8785 (в
терминах ECMAScript: сравнение через `Array.prototype.sort` без компаратора,
применённое к строкам ключей).

Важный нюанс для символов вне Basic Multilingual Plane (эмодзи, некоторые
редкие иероглифы, U+10000 и выше): в UTF-16 такие символы представлены
суррогатной парой (два code unit в диапазоне `0xD800–0xDFFF`). Так как этот
диапазон лежит *ниже* диапазона `0xE000–0xFFFF` (значительная часть обычных
BMP-символов), порядок по UTF-16 code units **не совпадает** с порядком по
Unicode code point для смешанных наборов ключей. Наивная сортировка
Python-строк по `sorted(keys)` (которая сравнивает по code point) даёт
неверный результат, если среди ключей есть символы вне BMP. Правильная
реализация сравнивает не сами строки, а их представление
`key.encode('utf-16-be')`.

Для тестовых векторов v0.1 все ключи — ASCII, поэтому оба способа сортировки
дают одинаковый результат; тем не менее референсная реализация обязана
использовать корректный UTF-16 компаратор, чтобы не ломаться на будущих
данных.

Сортировка и рекурсивная канонизация применяются на **каждом уровне
вложенности** независимо.

### 2. Представление чисел

JSON не различает «целое» и «дробное» число — это одна абстрактная
числовая величина. JCS требует, чтобы любое число, представимое как
IEEE-754 double (64-bit binary64), сериализовалось через алгоритм,
эквивалентный `ECMAScript Number::toString`:

- используется **кратчайшая** десятичная запись, однозначно
  восстанавливающая исходное значение double (round-trip);
- целые значения без дробной части и с «разумной» величиной сериализуются
  без десятичной точки и без экспоненты (`3`, а не `3.0` или `3e0`);
- `-0` сериализуется как `0` (JCS/ECMAScript не различают знак нуля в
  текстовом представлении);
- очень большие или очень маленькие по модулю числа переключаются на
  экспоненциальную запись вида `d.ddde+NN` / `d.ddde-NN` по тем же порогам,
  что и `Number.prototype.toString()` в ECMAScript;
- `NaN` и `±Infinity` в JSON не существуют — такие значения канонизировать
  нельзя, это ошибка входных данных.

**Ограничение точности:** double хранит целые числа точно только в
диапазоне `±2^53` (`±9 007 199 254 740 991`, `Number.MAX_SAFE_INTEGER`).
Если у вас есть значения вне этого диапазона (например теоретический
128-битный `entity_id`, если бы он передавался числом) — их **нельзя**
кодировать JSON-числом: они будут молча терять точность при проходе через
double-совместимый парсер на любом другом языке. Именно поэтому в схемах
BUIP `entity_id` и подобные идентификаторы — это **строки**, а не
числа (см. `schemas/entity.schema.json`).

### 3. Экранирование строк

Строки заключаются в двойные кавычки. Экранируется **минимально
необходимый** набор символов:

- `"` → `\"`
- `\` → `\\`
- управляющие символы `U+0000`–`U+001F`: символы `\b \f \n \r \t` — через
  короткие именованные escape-последовательности; остальные — через
  `\u00XX` (строчные hex-цифры, ровно 4 символа после `\u`, с ведущими
  нулями).

Всё остальное, включая непечатаемый диапазон выше `U+001F`, кириллицу,
эмодзи и любые не-ASCII символы, **не экранируется** и записывается как
литеральные UTF-8 байты. В частности:

- `/` (forward slash) не экранируется;
- `U+2028` (LINE SEPARATOR) и `U+2029` (PARAGRAPH SEPARATOR) не
  экранируются (в отличие от JS string-литералов в исходном коде — это
  другой контекст; `JSON.stringify` их не экранирует, и JCS тоже);
- символы вне BMP кодируются как есть в UTF-8 (в отличие от «сортировочного»
  представления по UTF-16 code units из правила 1 — это разные операции:
  сортировка ключей смотрит на UTF-16 code units, а итоговый *вывод*
  строки всегда в UTF-8).

### 4. Пробелы и разделители

Каноническая форма не содержит незначащих пробелов: никаких пробелов после
`:` и `,`, никаких переводов строк, никакого отступа. `{"a":1,"b":2}`, а не
`{"a": 1, "b": 2}`.

### 5. `null` и отсутствующие поля

`null` и «поле отсутствует» — **разные вещи** и не должны смешиваться:

- если ключ присутствует со значением `null`, он остаётся в объекте и
  канонизируется как `"key":null`;
- если ключ в объекте отсутствует, он отсутствует и в каноническом выводе —
  канонизация не добавляет и не удаляет ключи, не подставляет `null` вместо
  отсутствующих полей и не убирает `null`-значения.

Это намеренно оставлено на уровне схемы/бизнес-логики: если в схеме события
поле `MAY` отсутствовать, разработчик SDK должен явно решить, отправлять ли
`null` или не отправлять ключ вовсе — от этого зависит канонический хэш, и
задним числом сериализатор канонизации это решение не принимает.

### 6. Массивы

Массивы канонизируются поэлементно **в исходном порядке** (в отличие от
ключей объекта, порядок элементов массива — часть данных и не
переупорядочивается). Каждый элемент рекурсивно канонизируется по тем же
правилам.

### 7. Булевы значения

`true` / `false` — литерально, без изменений.

### 8. Кодировка

Итоговый канонический документ — это **байтовая строка UTF-8** без BOM
(byte order mark). Функция канонизации в референсной реализации возвращает
`bytes`, а не `str`, чтобы явно зафиксировать, что именно эти байты (а не
некая абстрактная "строка") подаются на вход хэш-функции/подписи.

### 9. Дубликаты ключей во входных данных

JCS определяет канонизацию для валидного JSON-объекта, где ключи уникальны
(это же требует RFC 8259). Поведение при дублирующихся ключах во входном
документе — вопрос парсера, предшествующий канонизации, а не самого JCS.
Референсная реализация канонизирует уже разобранный Python
`dict`, где дубликаты ключей исходного JSON были схлопнуты парсером
`json.loads` (побеждает последнее значение) — так же ведёт себя подавляющее
большинство JSON-парсеров. SDK на других языках должны придерживаться того
же правила ("последнее значение побеждает при разборе"), чтобы не получить
разный канонический результат для одного и того же входного текста.

## Итоговый рецепт

`digest(obj) = SHA-256(canonicalize(obj))`, где `canonicalize` — функция,
реализующая правила 1–8 выше, возвращающая `bytes` в UTF-8.

Проверить свою реализацию можно по `test-vectors/canonicalization.json` —
см. `test-vectors/README.md`.

## Что закладывается на будущее, но не решается в v0.1

- Компактный CBOR/COSE-профиль для edge/proof-сообщений (раздел 7
  протокольного ТЗ) — вне рамок этого документа, потребует отдельной
  спецификации канонизации для CBOR (детерминированный CBOR по RFC 8949
  §4.2, не JCS).
- Конкретный алгоритм подписи и его сериализация (`crypto_suite`,
  `signature`) — решение владельца протокола, см. раздел 15.2 протокольного
  ТЗ (Crypto Suite Registry). Канонизация payload'а не зависит от выбора
  алгоритма подписи: сначала канонизируется и хэшируется JSON, затем
  результат подписывается — эти два шага независимы.
