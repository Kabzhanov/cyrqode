# Версионирование схем и совместимость

## Где мы сейчас

Версия **0.x — черновик**. Схемы меняются без гарантии обратной совместимости,
включая ужесточение уже существующих полей. Пример такого изменения: поле
`crypto_suite` было свободной строкой, а после ADR 0001 стало перечислением —
это сужение контракта, и в стабильной версии оно потребовало бы новой ревизии.

Пока действует правило: **пишете свой SDK — фиксируйте commit репозитория**, а
не ссылайтесь на «последнюю версию». Так вы не проснётесь с несовместимостью.

## Что изменится с версии 1.0

С неё вступают правила, обычные для протоколов:

| Изменение | Можно в рамках минорной версии | Требует новой мажорной |
|---|---|---|
| добавить необязательное поле | да | — |
| добавить значение в перечисление | да | — |
| добавить новый профиль отрасли | да | — |
| сделать поле обязательным | нет | да |
| убрать поле или значение | нет | да |
| сузить формат существующего поля | нет | да |
| изменить правила канонизации | никогда: сломает все выпущенные подписи | — |

Канонизация вынесена отдельно намеренно. Её изменение делает недействительными
подписи всех ранее выпущенных событий, поэтому она не меняется вообще — вместо
этого вводится новый крипто-профиль.

## Как это выражено в файлах

- `$id` схемы содержит версию: `https://cyrqode.dev/schemas/v0.1/...`. Мажорная
  ревизия получит `v1`, и старые схемы останутся доступными по своим адресам —
  реализации, привязанные к ним, продолжат работать.
- Поле `schema_version` в самом событии указывает версию контракта, по которой
  событие сформировано. Сервер обязан принимать события прежних версий, пока они
  поддерживаются, и говорить об отказе явно, а не молча отбрасывать.

## Правило для сервера

Приняв событие, сервер не переписывает его под новую версию схемы. Событие
хранится ровно таким, каким пришло, вместе со своим `schema_version` — иначе
подпись перестанет проверяться, а журнал потеряет смысл.
