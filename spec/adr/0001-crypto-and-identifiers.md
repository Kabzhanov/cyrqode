# ADR 0001. Крипто-профили и генерация идентификаторов

Дата: 07.09.2026 · Статус: принято владельцем · Версия протокола: BUIP 0.1

## Почему это решение нельзя отложить

Канонизация, алгоритм подписи и формат идентификатора — публичный контракт.
Как только появится хотя бы один сторонний SDK, изменить их без поломки всех
интеграций станет невозможно: чужая реализация даст другой хэш, другую подпись
и другой вид идентификатора. Поэтому решение принимается до выпуска SDK.

## Решение 1. Два крипто-профиля сразу

| Профиль | Алгоритм | Где применяется |
|---|---|---|
| `ed25519-sha256-v1` | Ed25519 (RFC 8032), хэш SHA-256 | основной: серверы, SDK, мобильные приложения |
| `ecdsa-p256-sha256-v1` | ECDSA P-256, хэш SHA-256 | смарт-карты, NFC secure element, HSM |

**Почему два, а не один.** Ed25519 быстрее, компактнее (подпись 64 байта) и
детерминирован: подпись не зависит от качества генератора случайных чисел, а
плохой генератор на дешёвом терминале — реальный способ потерять ключ. Но
защита метки от клонирования (уровни PAL-4 и PAL-5) делается через secure
element, а массовые чипы умеют ECDSA P-256 и не умеют Ed25519. Выбери мы один
профиль — либо остались бы без аппаратной защиты, либо взяли бы менее стойкую
схему там, где она не нужна.

**Что подписывается.** Событие канонизируется по RFC 8785 без полей, которые
проставляет сервер (`received_time`, `committed_time`, `stream_sequence`) и без
самого `signature`. От полученных байтов берётся **SHA-256**, и подписывается
именно этот 32-байтовый дайджест — отсюда суффикс `-sha256-` в имени обоих
профилей.

Почему дайджест, а не сами байты: событие может нести объёмный payload, а
подпись фиксированного 32-байтового входа не зависит от его размера. Оба
профиля при этом ведут себя одинаково, что упрощает сторонние реализации.
Ed25519 внутри всё равно применяет SHA-512 — это часть алгоритма и не
настраивается; ECDSA использует режим `Prehashed(SHA-256)`.

Серверные поля исключены не для удобства: клиент физически не может подписать
то, чего ещё не существует. Практическое следствие для проверяющей стороны —
нельзя проверять подпись по записи из журнала целиком, сначала надо убрать
серверные поля.

**Детерминированность.** Ed25519 даёт одну и ту же подпись на один и тот же
вход, ECDSA — разные (случайный nonce). Это влияет на тесты: подпись Ed25519
можно сравнивать побайтово, подпись ECDSA — только проверять. Тестовые векторы
построены именно так.

**Задел.** Поле `crypto_suite` обязательно в каждом событии, чтобы добавление
постквантового профиля не потребовало менять формат.

## Решение 2. UUIDv7 для идентификаторов сущностей

Идентификатор — 128 бит, **UUIDv7** (RFC 9562), уникальность в пределах
пространства имён.

**Почему v7.** Старшие биты содержат время создания, поэтому идентификаторы
упорядочены. Для append-only журнала, который вырастет до миллионов записей,
это разница между индексом, дописываемым в конец, и индексом, который
перестраивается при каждой вставке.

**Чем платим.** UUIDv7 раскрывает момент создания сущности. Для партии продукции
это несущественно — дата выпуска и так на упаковке. Для сущности человека это
фактически дата приёма на работу, поэтому для чувствительных типов тенант может
включить **UUIDv4** политикой. Формат идентификатора при этом не меняется: обе
версии — те же 128 бит.

**Чего опасаться не нужно.** Подсчёта объёмов выпуска по идентификаторам:
он работает с последовательными номерами, а в UUIDv7 случайная часть остаётся
полноценной.

## Что это меняет в коде

- `crypto_suite` получает перечисление вместо свободной строки;
- в SDK появляются подпись и проверка для обоих профилей;
- публикуются тестовые векторы: канонические байты, хэш, подпись, открытый ключ;
- генерация идентификаторов переходит на UUIDv7 с возможностью v4.
