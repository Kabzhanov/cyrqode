# Схемы

| Файл | Что описывает |
|---|---|
| `entity.schema.json` | сущность: идентификатор, тип, пространство имён, статус |
| `event.schema.json` | **ядро** события: отраслево-нейтральное, без производственных полей |
| `event-committed.schema.json` | событие, уже принятое в журнал: требует серверных полей |
| `relationship.schema.json` | связь между сущностями с интервалом действия |
| `profile-manufacturing.schema.json` | производственный профиль поверх ядра |

## Почему ядро и «принятое» — разные схемы

Поля `received_time`, `committed_time` и `stream_sequence` проставляет сервер
при приёме. В момент, когда клиент формирует и подписывает событие, их ещё не
существует — значит требовать их от клиента нельзя.

Отсюда практическое следствие, важное для авторов SDK: **подпись клиента
покрывает только клиентские поля**. Проверять её нужно по тому же набору, а не
по записи из журнала целиком, иначе подпись никогда не сойдётся.

## Валидация без интернета

`$id` схем выглядят как адреса (`https://cyrqode.dev/schemas/...`), но это
**идентификаторы, а не места загрузки**. Валидатор не должен ходить в сеть.

Собирайте локальный store по `$id` — так делает `test-vectors/verify.py`:

```python
store = {}
for f in Path("schemas").glob("*.schema.json"):
    schema = json.load(open(f))
    store[schema["$id"]] = schema
```

Без этого `$ref` из производственного профиля на ядро попытается уйти в сеть и
проверка упадёт там, где интернета нет, — например, в цеху.

## Расширение под свою отрасль

Ядро не трогайте. Создайте профиль по образцу `profile-manufacturing.schema.json`:
подключите ядро через `allOf` и `$ref`, добавьте свои поля,
`unevaluatedProperties: false` закроет схему от случайных полей.
